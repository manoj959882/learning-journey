- **Process vs Thread** – Difference in memory, execution, and crash impact.  

Process → Independent execution unit, apna memory space rakhta hai.

Thread → Process ke andar ek chhota execution unit jo memory share karta hai.

| Feature 											| Process 						     	| Thread |

| **Creation Speed**								 | Slow (Resources allocate hote hain). | Fast (Bas Stack allocate hota hai). |
| **Communication** 								| Mushkil (OS ke through). 				| Bahut Aasaan (Direct variables). |
| **Crash Effect**								 | Doosre processes par koi effect nahi. 	| Poora process crash kar deta hai. |
| **Resource Consumption** 						| Zyada (Heavyweight). 						| Kam (Lightweight). |
										Example: Google Chrome ne 10 tabs kholi toh 10     		Example: Ek Chrome tab ke andar, ek thread HTML parse kar raha hai, 
										alag processes. Tab 1 ka memory Tab 2 ko nahi dikhta. 	doosra thread images download kar raha hai. Dono ek hi tab ka memory use kar rahe hain.

- **start() vs run()** – Why calling `run()` directly doesn’t create a new thread.  

 run() ek simple method hai jisme humara business logic hota hai. Agar hum direct run() call karte hain, toh JVM use normal method invocation ki tarah treat karta hai, 
 na ki thread start karne ka signal."
 
"Naya thread tabhi banta hai jab hum start() call karte hain, kyunki start() ek native method hai jo OS ke Thread Scheduler ko call karta hai."

"Direct run() call karne par, woh Current Thread (jaise Main Thread) ke stack par execute hota hai, isliye usme koi parallelism nahi aati."

"Aur agar hum direct run() call karke sochte hain ki thread chal gaya, toh humara program effectively Single-threaded reh jaata hai, aur humein multi-threading ka koi fayda nahi milta."


start() = "Main thread, JVM ko bolo ki ek nayi railway line (Thread) banaaye aur uss line pe ye train (run() method) daal de."
run() = "Main thread khud apni hi line pe train daal de, koi nayi line nahi banegee."

start() Method (Sahi Tarika)

Jab aap thread.start() call karte hain, toh internally 3 kaam hote hain:

1.Thread Registration: JVM (Java Virtual Machine) Operating System ko jaakar ek nayi native thread (OS level par) create karne ko bolta hai.

2.Stack Allocation: Is naye thread ko apna alag Call Stack (memory) mil jaati hai. Isme local variables aur method calls store hongi.

3.Scheduler Call: JVM uss naye thread ko Runnable state mein daal deta hai. Ab Thread Scheduler decide karega ki ye thread kab CPU par chale.

4.Automatic run() Call: Jab OS is thread ko CPU allot karti hai, toh woh automatically uss thread ka run() method execute karti hai.

Important: start() method immediately return ho jaati hai. Ye wait nahi karti ki run() khatam ho. Ye bas thread launch karti hai aur wapas aati hai.


❌ run() Method (Galti ka pitaara)
Jab aap direct thread.run() call karte hain:
Koi naya thread nahi banta.
JVM OS ko kuch nahi bolta.
Ye call bilkul normal method call ki tarah behave karti hai.
Jo current thread (mostly main thread) chal raha hai, wohi uss run() method ke andar ka saara code execute karega.
Jab tak run() ka code khatam nahi ho jaata, next line (uske baad wali code) execute nahi hogi.



- **Thread vs Runnable** – Pros/cons of extending `Thread` vs implementing `Runnable`.  

### 📌 Thread vs Runnable 

| Feature			 | Extending `Thread` 																											| Implementing `Runnable` |

| **Definition** 	| `class MyThread extends Thread { public void run() {...} }` 														| `class MyTask implements Runnable { public void run() {...} }` |
| **Inheritance** | **Drawback:** Java multiple inheritance nahi support karta. Agar aap `Thread` extend karte ho, toh kisi aur class ko extend nahi kar sakte. 	| **Advantage:** Aap kisi bhi doosri class ko extend kar sakte ho (flexibility). |
| **Reusability** | **Tight Coupling:** Thread logic aur business logic ek hi class mein merge ho jaate hain. 							| **Loose Coupling:** Business logic (Runnable) alag hai, Execution mechanism (Thread/Executor) alag. Runnable ko thread pool ya plain thread, kahin bhi daal sakte ho.
| **Resource Usage** | Har object ek alag thread hai. Thread create karna mehanga (heavyweight) hai. 							       | Runnable sirf ek **task** (lightweight object) hai. Isko baar-baar alag threads par daal sakte ho. |
| **When to use?** | Sirf tab jab aapko `Thread` class ki functionality override karni ho (e.g., `interrupt()`, `getName()) rarely used | **95% cases mein ye use hota hai.** Kyunki ye Enterprise applications (ExecutorService, ThreadPools) ke saath perfect fit baithta hai. |

# Callable Example

import java.util.concurrent.*;

class SumTask implements Callable<Integer> {

    @Override
    public Integer call() {
        return 10 + 20;
    }
}

public class Main {

    public static void main(String[] args) throws Exception {

        ExecutorService executor = Executors.newSingleThreadExecutor();

        Future<Integer> future = executor.submit(new SumTask());

        Integer result = future.get();

        System.out.println(result);

        executor.shutdown();
    }
}

# Future

A `Future` represents the result of an asynchronous computation.

Think of it like ordering food online:

* Place the order (`submit()`)
* Continue doing other work
* Check later when it's ready (`get()`)

One of the biggest advantages of `Callable`:

Now:

```java
try {
```

- **Volatile keyword** – Visibility guarantees across threads.  

volatile keyword JVM aur CPU ko batata hai ki is variable ki value directly main memory (RAM) se read aur write kare, thread-local cache me store nahi kare.
 Isse ek thread ki, ki gayi writing doosre threads ko turant dikhti hai, lekin ye atomicity guarantee nahi karta.
 
 Without volatile:

10 employees (threads) ek hi whiteboard (main memory) dekh rahe hain.

Har employee ke paas apna personal notepad (CPU cache) hai.

Boss (Thread 1) ne whiteboard par likha "Meeting cancel", lekin usne apne notepad me likha, whiteboard par nahi.

Baki 9 employees apna personal notepad dekhte rahe, unhe pata nahi chala meeting cancel hai. Visibility issue!

With volatile:

Boss ne whiteboard par hi directly likha.

Baki saare employees whiteboard se hi read karte hain.

Sabko real-time update dikhta hai!

 3. volatile vs synchronized (Most Asked Comparison)
Feature					volatile								synchronized
Visibility		✅ Guarantee (Main memory read/write)	✅ Guarantee (Lock acquire karne par cache flush)
Atomicity		❌ No (i++ multiple operations hain)	✅ Yes (Poora block ek atomic unit hai)
Performance		🚀 Lightweight (No locking)				🐢 Heavy (Lock acquire/release me overhead)

Problem: Without volatile (Infinite Loop)
public class VolatileProblem {
    private static boolean flag = true; // volatile nahi hai

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (flag) {  // Yeh loop kabhi nahi rukega!
                // CPU is flag ko apne cache me store kar leta hai
            }
            System.out.println("Thread stopped!");
        });
        worker.start();

        Thread.sleep(2000);
        flag = false; // Main thread ne flag false kiya
        System.out.println("Flag set to false, but worker thread is stuck!");
    }
}

Solution: With volatile
public class VolatileSolution {
    private static volatile boolean flag = true; // volatile lagaya

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (flag) {  // Ab har iteration me main memory se read karega
                // Isliye flag change detect ho jayega
            }
            System.out.println("✅ Thread stopped successfully!");
        });
        worker.start();

        Thread.sleep(2000);
        flag = false; // Main memory me direct write hoga
        System.out.println("Flag set to false, worker thread stopped!");
    }
}

}

✅ Correct Usage (Synchronized / AtomicInteger)

}

******What is ExecutorService?  ****

ExecutorService is a thread pool manager.

Instead of creating a new thread for every task, it maintains a pool of reusable threads.

Imagine you have 5 employees and 100 tasks:
Tasks
 │
 ▼
ExecutorService
 │
 ├── Thread-1
 ├── Thread-2
 ├── Thread-3
 ├── Thread-4
 └── Thread-5
 
 Only 5 threads are created, and they keep taking tasks until all work is complete.


public class Main {

    public static void main(String[] args) {

        ExecutorService executor = Executors.newFixedThreadPool(3);

        for (int i = 1; i <= 10; i++) {

            int task = i;

            executor.submit(() -> {
                System.out.println(
                    "Task " + task +
                    " executed by " +
                    Thread.currentThread().getName()
                );
            });
        }

        executor.shutdown();
    }
}

How it Works
10 Tasks
   │
   ▼
ExecutorService
   │
   ├── Thread-1
   ├── Thread-2
   └── Thread-3

After Thread-1 finishes Task-1,
it immediately picks Task-4.
Threads are reused, which is much more efficient.

Creating an ExecutorService with Fixed Thread Pool

- **wait(), notify(), notifyAll()** – Inter-thread communication basics.  
wait(), notify(), aur notifyAll() Object class ki methods hain jo inter-thread communication ke liye use hoti hain. Ye synchronized context me hi kaam karti hain.
 wait() thread ko waiting state me daal deta hai aur lock release kar deta hai, notify() ek waiting thread ko wake up karta hai, aur notifyAll() saare waiting threads ko wake up karta hai

📊 3. Important Points 
Method						Kya Karta Hai						Lock Release?															Kaise Use Karein
wait()				Thread ko waiting state me daalta hai	✅ Lock release kar deta hai												synchronized block me hi call karein
wait(timeout)		Specified time tak wait karega			✅ Lock release																Timeout ke baad automatically wake up
notify()			Ek randomly selected waiting thread ko wake up karta hai	❌ Lock release nahi karta (block khatam hone par)		synchronized block me hi call karein
notifyAll()			Saare waiting threads ko wake up karta hai		❌ Lock release nahi karta											Sabko chance do, ek lock lega


⚠️ 4. Golden rule
Rule 1: "Ye methods Object class me hain kyunki lock kisi bhi object ka ho sakta hai. Thread class me nahi hain kyunki thread object par bhi lock ho sakta hai."
Rule 2: "Inhe synchronized block/method ke andar hi call karna padta hai, warna IllegalMonitorStateException aayegi."
Rule 3: "wait() call karne par thread lock release kar deta hai, lekin notify() call karne par lock immediately release nahi hota – synchronized block khatam hone par release hota hai."
Rule 4: "Spurious wakeup possible hai – thread bina notify ke bhi wake up ho sakta hai. Isliye hamesha wait() ko while loop me use karein."


public class WaitNotifyExample {
    private static final Object lock = new Object();
    private static int data = 0;
    private static boolean produced = false;

    public static void main(String[] args) {
        Thread producer = new Thread(() -> {
            for (int i = 1; i <= 5; i++) {
                synchronized (lock) {
                    while (produced) {  // ✅ while loop - Spurious wakeup se bachne ke liye
                        try {
                            lock.wait(); // Data consume hone tak wait
                        } catch (InterruptedException e) {
                            Thread.currentThread().interrupt();
                        }
                    }
                    data = i;
                    produced = true;
                    System.out.println("✅ Produced: " + data);
                    lock.notify(); // Consumer ko wake up karo
                }
            }
        });

        Thread consumer = new Thread(() -> {
            for (int i = 1; i <= 5; i++) {
                synchronized (lock) {
                    while (!produced) {  // ✅ while loop
                        try {
                            lock.wait(); // Data produce hone tak wait
                        } catch (InterruptedException e) {
                            Thread.currentThread().interrupt();
                        }
                    }
                    System.out.println("🔹 Consumed: " + data);
                    produced = false;
                    lock.notify(); // Producer ko wake up karo
                }
            }
        });

        producer.start();
        consumer.start();
    }
}


- **Deadlock** – Causes, detection, and prevention strategies.  
 deadlock tab hota hai jab do ya zyada threads ek-doosre ka lock hold karte hue doosre ka lock wait kar rahe hain, aur koi bhi thread apna lock release nahi kar raha. 
 Ye circular wait condition create ho jaati hai, aur sab threads permanently block ho jaate hain.
 

3. Deadlock Ke 4 Conditions (Coffman Conditions)
 deadlock tab hota hai jab ye 4 conditions simultaneously satisfy hoti hain. Agar ek bhi condition break kar di, toh deadlock nahi aayega!"

Condition				Explanation									Example
1. Mutual Exclusion	Resource sirf ek thread use kar sakta hai			Ek lock ek time par ek thread ke paas
2. Hold & Wait		Thread ek lock hold karke doosra lock wait kare		Bat hold karke Ball wait karna
3. No Preemption	Koi doosra thread forcefully lock nahi le sakta		Baccha A se bat forcefully nahi cheen sakte
4. Circular Wait	Threads circular dependency mein fasein				A waits for B, B waits for A


public class DeadlockExample {
    private static final Object LOCK1 = new Object();
    private static final Object LOCK2 = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK1) {  // Thread 1 ne LOCK1 le liya
                System.out.println("Thread 1: Holding LOCK1...");
                try { Thread.sleep(100); } catch (Exception e) {} 
                synchronized (LOCK2) {  // Ab LOCK2 chahta hai
                    System.out.println("Thread 1: Holding LOCK1 & LOCK2");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (LOCK2) {  // Thread 2 ne LOCK2 le liya
                System.out.println("Thread 2: Holding LOCK2...");
                
                try { Thread.sleep(100); } catch (Exception e) {}
                
                synchronized (LOCK1) {  // Ab LOCK1 chahta hai
                    System.out.println("Thread 2: Holding LOCK1 & LOCK2");
                }
            }
        });

        t1.start();
        t2.start();
        // Output: Dono threads hung ho jayenge! 🥴
    }
}


**ConcurrentHashMap** – Internal working and segment locking.  
ConcurrentHashMap ek thread-safe Map hai jo high concurrency ke liye design ki gayi hai. Ye multiple threads ko read/write allow karta hai bina poori map ko lock kiye.
 Java 8+ me ye CAS (Compare-And-Swap) + synchronized on nodes use karta hai, aur null keys/values allow nahi karta.

ConcurrentHashMap vs Hashtable vs synchronizedMap:

Feature						ConcurrentHashMap								Hashtable							Collections.synchronizedMap()
Thread-Safety			✅ Yes (Segmented/Bucket level locking)				✅ Yes (Entire map locking)			✅ Yes (Entire map locking)
Performance				🚀 High (Multiple threads parallel access)			🐢 Low (Single thread at a time)	🐢 Low (Single thread at a time)
Null Keys/Values			❌ Not allowed									❌ Not allowed						✅ Allowed
Read Operations				✅ No locking (Volatile reads)					🔒 Lock required					🔒 Lock required
Iterator				✅ Weakly consistent (No ConcurrentModificationException)  🔒 Fail-fast (Exception aayegi)	🔒 Fail-fast


Structure Batao:
ConcurrentHashMap
    |
    ├── Node[] table  (Array of buckets/nodes)
    |       |
    |       ├── Node (key, value, hash, next)
    |       ├── TreeNode (for TreeBin)
    |       └── TreeBin (when bucket size > 8, converts to Red-Black Tree)
    |
    └── sizeCtl (Control flag for resizing)	

	
public class ConcurrentHashMapExample {

    public static void main(String[] args) {
	
        ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
        map.put("A", 1); // ✅ put - Thread-safe
        map.put("B", 2);
        
        // ✅ get - Thread-safe, no lock
        Integer value = map.get("A");
        System.out.println("Value: " + value); // 1
        
        // ✅ putIfAbsent - Atomic operation
        map.putIfAbsent("A", 100); // Nahi change hoga kyunki "A" already hai
        System.out.println(map.get("A")); // Still 1
        
        // ✅ replace - Atomic check-and-set
        map.replace("A", 1, 100); // Replace if current value is 1
        System.out.println(map.get("A")); // 100
    }
}

// ✅ Way 3: Implement Callable (Returns result)
class MyCallable implements Callable<Integer> {
    @Override
    public Integer call() throws Exception {
        System.out.println("Callable running: " + Thread.currentThread().getName());
        return 42; // Return result
    }
}

// Usage
public class CallableDemo {
    public static void main(String[] args) throws Exception {

        Future<Integer> future = executor.submit(new MyCallable());

        Integer result = future.get();
        System.out.println("Result: " + result);

    }

## Classic Synchronization Problems (Core Concepts)

1. **Producer-Consumer Problem** — using `wait()`/`notify()`, then redo with `BlockingQueue`
2. **Print numbers in order using multiple threads** (e.g., Thread1 prints odd, Thread2 prints even, alternating 1,2,3,4...)
3. **Print 1 to N using 3 threads in sequence** (thread A prints multiples of 3, B of 5, C the rest — FizzBuzz style with threads)
4. **Dining Philosophers Problem** — classic deadlock scenario, solve using resource ordering or semaphores
5. **Readers-Writers Problem** — multiple readers can read simultaneously, but writers need exclusive access
6. **Bounded Buffer Problem** — same as producer-consumer but with a fixed-size buffer

## Thread Coordination & Communication

7. **Two threads printing "Ping" and "Pong" alternately**
8. **Implement a Barrier from scratch** (like `CyclicBarrier`) — N threads wait until all reach a point
9. **Implement your own simple Semaphore** using `wait()`/`notify()`
10. **Thread that waits for another thread to finish (join simulation)** without using `.join()`

## Practical/API-based Problems

11. **Implement a thread-safe Singleton** (double-checked locking, and compare with enum-based singleton)
12. **Design a thread-safe Counter** — compare synchronized method vs `AtomicInteger`
13. **Implement a simple thread pool from scratch** (understand what `ExecutorService` does internally)
14. **Design a rate limiter** using threads (token bucket concept)
15. **Implement a Blocking Queue from scratch** (don't use `java.util.concurrent.BlockingQueue`)

## Deadlock, Race Conditions & Debugging

16. **Write code that causes a deadlock intentionally, then fix it** (classic: two locks acquired in different order by two threads)
17. **Demonstrate a race condition** (e.g., unsynchronized counter incremented by multiple threads) and fix it three ways: `synchronized`, `Lock`, `AtomicInteger`
18. **Detect and avoid livelock** — write a scenario and resolve it

## Advanced/Design-Oriented

19. **Design a multithreaded web crawler** (or file downloader) using `ExecutorService` and `Future`
20. **Implement a Cache with expiry using multiple threads** (thread-safe read/write, eviction logic)

How do you trigger builds (webhooks, polling SCM, cron jobs)?
  Jenkins builds trigger karne ke 3 main tareeke hain: Webhooks (Git push par automatic trigger), Polling SCM (periodically check kare ki changes aaye hain), 
  aur Cron jobs (scheduled time par trigger, jaise nightly builds). Production me webhooks prefer karte hain kyunki ye real-time aur efficient hain
  
  Point 1 (Webhooks - Best):
"Webhooks best hain kyunki ye event-driven hain. Developer push karega, turant build trigger ho jayega. Jenkins ko unnecessary polling nahi karni padti, isse server load kam hota hai."

Point 2 (Polling SCM - Fallback):
"Jab webhooks configure nahi kar sakte (e.g., corporate firewall), tab polling use karte hain. Lekin ye inefficient hai kyunki Jenkins baar-baar Git check karega chahe changes aaye ya nahi."

Point 3 (Cron - Scheduled):
"Cron jobs scheduled builds ke liye hain – daily regression tests, nightly integration builds, ya weekly security scans.

Kubernetes (K8s) is an open-source container orchestration platform that automates the deployment, scaling, management, networking, and monitoring of containerized applications.
Kubernetes ka use containerized applications ko efficiently manage karne ke liye hota hai.

Agar aapke paas hundreds ya thousands of containers hain, to unhe manually manage karna bahut difficult ho jata hai.

Kubernetes ye saare tasks automatically handle karta hai.

Kubernetes provides:
✅ Automatic Deployment
✅ Auto Scaling
✅ Load Balancing
✅ Self-Healing
✅ Service Discovery
✅ Rolling Updates & Rollbacks
✅ High Availability
✅ Resource Management

Agar ek container crash ho jaye ya traffic suddenly 10x badh jaye, to Kubernetes automatically:

Restart karega crashed container.
Extra container instances create karega.
Load balance karega requests.
Healthy containers ko traffic bhejega.

Developer ko manually kuch karne ki zarurat nahi hoti.

Deployments and ReplicaSets
ReplicaSet ensures specified number of pod replicas are always running. Deployment is a higher-level controller that manages ReplicaSets and 
provides rolling updates, rollback, scaling, and self-healing capabilities.

Deployment (Manages)
    ↓
ReplicaSet (Manages)
    ↓
Pods (Actual containers)


Component	Role
ReplicaSet	Ensures n pods are always running
Deployment	Manages ReplicaSets → Rolling updates, Rollback, Scaling


How It Works (Key Features):

Feature	How Deployment Does It
Scaling	Change replicas: 5 → Deployment updates ReplicaSet
Rolling Update	New ReplicaSet created → Old pods gradually replaced → Zero downtime
Rollback	kubectl rollout undo deployment/myapp → Reverts to previous ReplicaSet
Self-Healing	Pod crash → ReplicaSet creates new pod automatically
Pause/Resume	kubectl rollout pause → Stop updates temporarily


# Create deployment
kubectl create deployment myapp --image=nginx

# Scale
kubectl scale deployment myapp --replicas=5

# Rolling update (change image)
kubectl set image deployment/myapp nginx=nginx:1.21

# Check rollout status
kubectl rollout status deployment/myapp

# Rollback to previous version
kubectl rollout undo deployment/myapp

# Rollback to specific revision
kubectl rollout undo deployment/myapp --to-revision=2

# View rollout history
kubectl rollout history deployment/myapp

# Pause rollout
kubectl rollout pause deployment/myapp

# Resume rollout
kubectl rollout resume deployment/myapp



Service Discovery and Load Balancing
Kubernetes Service ek abstraction hai jo pods ke dynamic IP addresses ko stable endpoint provide karta hai. Ye service discovery (DNS) aur load balancing (round-robin) provide karta hai.
 3 main types hain – ClusterIP (internal), NodePort (external testing), LoadBalancer (cloud production).



================================================================================
                     KUBERNETES SERVICE TYPES (COMPARISON)
================================================================================

+----------------+---------------------------+-----------------------------------------------+-------------------------------------------+
| Service Type   | Access                    | Use Case                                      | Example                                   |
+----------------+---------------------------+-----------------------------------------------+-------------------------------------------+
| ClusterIP      | Internal (Within Cluster) | Internal communication between microservices  | Backend Service -> Database               |
|                |                           | (Default Kubernetes Service Type)             |                                           |
+----------------+---------------------------+-----------------------------------------------+-------------------------------------------+
| NodePort       | External                  | Development, Testing, Demo                    | http://<NodeIP>:30080                     |
|                | (Node IP : Port)          | Access application using Node IP and Port     | curl http://192.168.1.10:30080            |
+----------------+---------------------------+-----------------------------------------------+-------------------------------------------+
| LoadBalancer   | External                  | Production applications on Cloud              | http://myapp-lb.amazonaws.com             |
|                | (Cloud Load Balancer)     | (AWS, Azure, GCP, OpenShift)                  |                                           |
+----------------+---------------------------+-----------------------------------------------+-------------------------------------------+
| ExternalName   | External DNS              | Access external services using internal alias | db.external.com -> database.company.com   |
|                |                           | No proxying, only DNS CNAME mapping           |                                           |
+----------------+---------------------------+-----------------------------------------------+-------------------------------------------+

Security in Kubernetes

RBAC, NetworkPolicies, PodSecurityPolicies, and certificate management.

Kubernetes security ke 4 pillars hain – RBAC (who can do what), NetworkPolicies (who can talk to whom), PodSecurity (what pods can do), aur Certificate Management (secure communication). Inko combine karke zero-trust security enforce karte hain.
The 4 Security Pillars

Kubernetes Security
├── 1. RBAC (Authentication + Authorization)
│   └── Who can access what?
├── 2. Network Policies
│   └── Which pods can talk to each other?
├── 3. Pod Security (PSP/PSA)
│   └── What can pods do? (root? privileged?)
└── 4. Certificate Management (mTLS)
    └── Encrypted communication between components

1. RBAC (Role-Based Access Control)
Who can do what?

Component	Role
Role	Defines permissions in a namespace
ClusterRole	Defines permissions cluster-wide
RoleBinding	Binds Role to user/service account
ClusterRoleBinding	Binds ClusterRole cluster-wide
Example:
# ✅ Role (Namespace level)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

# ✅ RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: read-pods
subjects:
- kind: User
  name: developer@company.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
  
 
Built-in ClusterRoles:
 cluster-admin   → Full access
admin           → Namespace admin
edit            → Read/write access
view            → Read-only access

````text
================================================================================
                    KUBERNETES NETWORK POLICIES (ZERO TRUST)
================================================================================

Definition
----------
NetworkPolicy controls Pod-to-Pod communication in Kubernetes.

By Default
----------
❌ All Pods can communicate with each other.

Why Use NetworkPolicy?
----------------------
✓ Restrict Pod-to-Pod communication
✓ Improve Security
✓ Implement Zero-Trust Networking
✓ Allow only required traffic

Interview Answer
----------------
"By default, Kubernetes allows all Pods to communicate with each other.
NetworkPolicy is used to control which Pods can send or receive traffic,
implementing a Zero-Trust network model."

================================================================================
DENY ALL NETWORK POLICY
================================================================================

Purpose
-------
Blocks all incoming (Ingress) and outgoing (Egress) traffic for all Pods.

YAML
----

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: deny-all

spec:
  podSelector: {}        # Selects all Pods

  policyTypes:
  - Ingress
  - Egress

  # No ingress/egress rules
  # => All traffic is blocked
```

Flow

Client
   |
   X
Backend Pod

Result
------
❌ No Pod can communicate with any other Pod.

================================================================================
ALLOW SPECIFIC NETWORK POLICY
================================================================================

Purpose
-------
Allows only Frontend Pods to access Backend Pods.

YAML
----

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: allow-frontend

spec:
  podSelector:
    matchLabels:
      app: backend

  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend

    ports:
    - port: 8080
```

Flow

Frontend Pod
      |
      |  Allowed
      V
Backend Pod

Database Pod
      |
      X
Backend Pod

Result
------
✔ Frontend -> Backend (Allowed)
❌ Others -> Backend (Blocked)

POD SECURITY (PSP -> PSA)
================================================================================

Definition
----------
Pod Security controls what a Pod is allowed to do.

Important
---------
PodSecurityPolicy (PSP) is DEPRECATED.

Modern Kubernetes uses:

✔ Pod Security Admission (PSA)

PSA works using Namespace Labels.

================================================================================
POD SECURITY LEVELS
================================================================================

+---------------+-------------------------------------------------------------+
| Level         | Description                                                 |
+---------------+-------------------------------------------------------------+
| Privileged    | No restrictions (Not Recommended)                           |
| Baseline      | Blocks common privilege escalation attacks                  |
| Restricted    | Strongest security (Recommended for Production)             |
+---------------+-------------------------------------------------------------+

================================================================================
RESTRICTED PSA EXAMPLE
================================================================================

```yaml
apiVersion: v1
kind: Namespace

metadata:
  name: prod

  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
```

================================================================================
WHAT DOES RESTRICTED ENFORCE?
================================================================================

✔ runAsNonRoot: true
✔ runAsUser: 1001+
✔ readOnlyRootFilesystem: true
✔ Drop Linux Capabilities
✔ seccompProfile: RuntimeDefault

Benefits
--------
✓ Better Security
✓ Prevents Root Containers
✓ Prevents Privilege Escalation
✓ Protects Host OS
````

What is Docker and why is it used?

Docker ek containerization platform hai jo applications ko isolated, lightweight containers me package karta hai. 
Isme application aur uski dependencies (libraries, configs) saath me ship hoti hain, jo any environment me consistently run hoti hain – developer laptop se lekar production server tak.

# IMAGE Commands
docker images                  # List all images
docker build -t myapp:1.0 .    # Build image from Dockerfile
docker pull nginx:latest       # Pull image from registry
docker push myapp:1.0          # Push image to registry
docker rmi myapp:1.0           # Remove image

# CONTAINER Commands
docker ps                      # List running containers
docker ps -a                   # List all containers (including stopped)
docker run -d myapp:1.0        # Create + start container from image
docker start myapp             # Start existing container
docker stop myapp              # Stop running container
docker rm myapp                # Remove container
docker exec -it myapp bash     # Execute inside running container
docker logs myapp              # View container logs





Docker Image vs Container

Docker Image ek read-only template hai jisme application aur uski dependencies hoti hain. Container us image ka running instance hai – ek live, executable process

How It Works (Layered Architecture)::
┌─────────────────────────────────────────────┐
│           DOCKER IMAGE (Read-Only)           │
├─────────────────────────────────────────────┤
│  Layer 5: Application Code                   │
│  Layer 4: Dependencies (jar, node_modules)   │
│  Layer 3: OS Packages (apt, yum)             │
│  Layer 2: Base Image (Ubuntu, Alpine)        │
│  Layer 1: Kernel (Shared with host)          │
└─────────────────────────────────────────────┘
                    │
                    ▼ docker run
┌─────────────────────────────────────────────┐
│        DOCKER CONTAINER (Read-Write)         │
├─────────────────────────────────────────────┤
│  Read-Write Layer (Changes, Logs, Files)     │
│  ───────────────────────────────────────────  │
│  Layer 5: Application Code                   │
│  Layer 4: Dependencies                       │
│  Layer 3: OS Packages                        │
│  Layer 2: Base Image                         │
│  Layer 1: Shared Kernel                      │
└─────────────────────────────────────────────┘
Multiple containers share the same image layers, but each has its own read-write layer for runtime changes (logs, temp files).


Explain containerization, portability, and difference from virtual machines.

Containerization ek lightweight virtualization technique hai jo application aur uski dependencies ko isolated units (containers) me package karta hai. 
Portability means ye containers kisi bhi environment (developer laptop, testing server, production cloud) me consistently run hote hain. Virtual machines ki tarah nahi,
kyunki containers host OS kernel share karte hain, isliye lightweight aur fast hain.
